# Verification

Run commands from the repository root after the submodule bootstrap in [README.md](../README.md). The Go floor is in `go.mod`; CircleCI is the CI owner. [IMPLEMENTATION.md](../IMPLEMENTATION.md) records actual evidence and outstanding requirements. Commands inherit the trusted operator environment, but diagnostics print only selected kernel/resource observations and validated verification settings.

## Contributor commands

```sh
make dep
make test-environment
make vet
make lint
make scripts-lint
make specs
make coverage
make compile
make sec
```

`make dep` uses the shared download/tidy/vendor workflow. Toolchain selection and resolution of the pinned `golang.org/x/sys` dependency may require network access to Go's module proxy/checksum services. Environment discovery requires `uname` and `true` on PATH. `make scripts-lint` requires ShellCheck. `make sec` uses govulncheck and Trivy and may download vulnerability databases. The CI image supplies the quality tools listed in the README; local tool absence is a verification gap, not a pass. `make ci-validate` uses the official CircleCI CLI and its validation API when the CLI/access are available.

`make specs` retains the shared gotestsum runner, race detection, and coverage. It also writes all test events, including output and skips, to `test/reports/specs.json`, alongside `specs.xml` and `profile.cov`. A skipped test is not kernel runtime coverage. Each run replaces those files: archive a run before changing profiles/toolchains if its evidence must be retained. CircleCI stores each job's reports separately. Scope tests with `package=internal/testenv make specs` (or a later implemented package path). The `.gocov` filter excludes the `/test/` directory, retaining coverage of the implemented environment checker and command even though their names contain `test`. `make compile` builds each package and its tests into unique temporary paths for both linux/amd64 and linux/arm64 with cgo disabled, then removes them. It never executes the resulting binaries and is not race/runtime coverage.

Reusable resource factories, cleanup, descriptor inspection, bounded asynchronous reads, subprocesses, and mount-namespace setup live in [internal/test](../internal/test). Focused ABI fixtures snapshot procfs descriptors around acquisition after initializing Go polling. They inspect the original descriptor without duplication while cleanup retains its owner, and prohibit concurrent closure during raw observations. Ordinary concurrency scenarios continue through typed public operations; production owners expose no shared inspection interface. Package tests retain their behavior assertions and named input tables. Use descriptive test names because gotestsum prints them as the behavior report. Group related method checks in compact assertion tables when separate passing subtests would obscure the scenario. Executable examples keep ordinary caller code instead of depending on test fixtures.

## Profiles and prerequisite results

| Setting | Values and behavior |
| --- | --- |
| `profile` | `rootless` (default): ordinary-user checks; `namespaces`: additionally request namespace creation/mapping and isolated mount integration |
| `required` | `false` (default): a known unavailable selected prerequisite skips its affected test with a precise reason; `true`: the same result fails the test and command |
| `arch` | Empty (default), `amd64`, or `arm64`; a supplied value must match both the executing Go binary and `uname -m` |
| `kernel` | `supported` (default): Linux 7.0 or later; `7.0`: exactly the baseline major/minor; `newer`: newer than 7.0. A mismatch fails even when the profile is optional. |

Make exports these as `GO_LINUX_TEST_PROFILE`, `GO_LINUX_TEST_REQUIRED`, `GO_LINUX_TEST_ARCH`, and `GO_LINUX_TEST_KERNEL` for the Go command/tests. Invalid settings fail before probing. Set the Make variables at the documented entrypoints rather than relying on inherited values for those four variables.

```sh
make test-environment profile=namespaces
make specs profile=namespaces
make specs profile=namespaces required=true
make specs profile=rootless required=true arch=arm64 kernel=7.0
```

After `make dep`, run `make verify-mount` on a capable Linux host to record namespace prerequisites and run only the mount package's required namespace-profile tests. It creates `test/reports/`, writes the environment report to `test/reports/environment.json`, and runs the existing race/coverage harness only after discovery succeeds. Discovery or report-writing failure stops the command before tests; unavailable prerequisites fail rather than skip. The target always selects `profile=namespaces`, `required=true`, and `package=mount` for tests. It accepts the existing `arch` and `kernel` selectors; omit `arch` for the current host or use `make verify-mount arch=arm64` to match CI. It neither starts Docker nor changes host privileges; local namespace restrictions can still prevent execution.

`kernel=newer` remains an optional selector for an available newer-kernel runner or local checks. It is not a required CI lane. The required runtime target is the available Linux 7.0 arm64 CircleCI runner; update the target and recorded evidence when that runner environment changes.

These are requests to verify an environment, not proof that such runners exist. Default rootless tests can pass on UID 1000 without capabilities. The profile selects tests intended for ordinary users; execution on UID 0 does not establish ordinary-user runtime coverage, so retain the actual UID/capability observations with the results. Namespace creation is probed even during rootless discovery, but a known namespace denial does not invalidate rootless coverage. The namespace profile requests an actual `clone` with user/mount/network namespace flags and one-entry UID/GID mappings; the child executes `true` and exits, with a five-second bound and deterministic process reaping. It performs no mount or network mutation. Successful discovery establishes only creation/mapping prerequisites, not that every filesystem, namespace transition, or privileged facility works.

Diagnostics include Go version, kernel, machine and Go architectures, UID, effective/bounding capabilities, no-new-privileges, seccomp mode, namespace identifiers, selected mount types/options, and cgroup v2 controller observations. Read-only mount/controller observations do not establish writable delegation. The namespace probe's observed error remains visible. It classifies `EPERM`, `EACCES`, `ENOSYS`, or `ENOSPC` from that precise creation/mapping attempt as unavailable prerequisites; it does not infer the responsible seccomp rule or policy. Missing executables, timeouts, unexpected child failures, `EINVAL`, and other unexplained errors fail. An expected permission denial is distinct from successful isolation coverage.

Later package tests must perform their own operation-specific prerequisite checks; do not turn any facility `EPERM` into a blanket skip. Add capability or delegated-resource profiles when an implemented operation first needs them, with its real isolated/delegated resource checks. F02 does not create speculative privilege fixtures for the remaining packages. Mount, route mutation, cgroup delegation, and clock-changing success paths remain separate verification obligations.

`package=mount make specs` runs ordinary-user validation, zero-owner/error behavior, real failed fsopen/open_tree errno propagation, closed-directory borrowing, and descriptor cleanup. It explicitly skips the named integration behaviors because successful mount operations need the namespace profile. `package=mount make specs profile=namespaces` runs each integration behavior in a bounded subprocess with new user/mount namespaces and one-entry UID/GID mappings, using the shared internal fixture. It verifies isolation, makes propagation private, and probes fsopen(tmpfs) before exercising the library. Precise namespace creation/mapping or private-propagation/fsopen prerequisite denials can skip only in optional mode. Add `required=true` to fail when they are unavailable. All later library-operation errors fail, including permission errors; no blanket mount skip follows successful prerequisites.

The mount fixture covers configuration/creation, acquisition flags and failure cleanup, diagnostics/queue order, concurrent diagnostic attribution/Close, all selected attributes, recursive scope, typed root metadata/attribute snapshots, normal/detached unmount ownership, attachment persistence after Close, single/recursive cloning, directory borrowing, and descriptor exhaustion. It invokes the executable examples inside isolation and unmounts attached resources before removing directories. Local namespace creation returns EPERM, and Docker CI denies private propagation for its ordinary user. Required mount verification therefore runs separately on a privileged VM-backed root container, preserving the fixture's namespace isolation. At ae50d8d, [Go 1.27.0 job 195](https://circleci.com/gh/alexfalkowski/go-linux/195) and [Go 1.27.4 job 192](https://circleci.com/gh/alexfalkowski/go-linux/192) each pass all 39 mount events with no failures/skips on actual Linux 7.0.0-1004-aws arm64. P06 is complete for that observed target. See the [mount guide](mount.md), [design note](design/mount.md), and P06 handoff.

`package=memfd make specs` exercises creation, ordinary I/O, sealing, mappings affected by seals, executable opt-in, and lifecycle without additional profiles or skips. It requires permitted `memfd_create`/`fcntl`/`mmap` operations and policy allowing `MFD_EXEC`; denial fails rather than claiming that mode is verified. Tests never execute a memfd or modify host security policy. `package=timerfd make specs` exercises all three ordinary clocks, relative/absolute and one-shot/periodic arming, previous/current state, count consumption and reset, invalid inputs and limits, raw flags, deadlines, concurrent operations, and shutdown. `package=mmap make specs` exercises both anonymous modes, shared file visibility/private copies, page-aligned offsets and exact slice bounds, file/mapping lifetime independence, permissions, all five advice operations, invalid arguments, zero/closed owners, concurrent methods/source closure, and complete unmapping/construction cleanup. `package=pidfd make specs` exercises handle acquisition/adoption, signal delivery to test-owned children, exit observation without reaping, normal/signal/core-dump child status, competing and external reapers, non-child observation, concurrent close interruption, standard-library handle composition, flags, and descriptor cleanup. ## CI and outstanding runners

The quality build and ordinary-user `verify` matrix use the Docker executor, image `alexfalkowski/go:5.23`, resource class `arm.large`. Verification requests Go 1.27.0 (minimum) and Go 1.27.4 (latest stable checked on 2026-11-14), using [GOTOOLCHAIN](https://go.dev/doc/toolchain). It runs dependency setup, environment discovery, vet, both compile architectures, and `make specs profile=rootless required=true arch=arm64`. Mount integration is selected separately. Update the pins when the Go floor or latest supported release changes; the [Go release feed](https://go.dev/dl/?mode=json) is the reference.

The required `verify-mount` matrix uses the same Go versions on the `machine` executor, image `ubuntu-2604:current`, resource class `arm.medium`. It runs the existing Go image with `docker run --rm --privileged --user root` so this mount-only lane has effective mount capabilities. Ordinary-user behavior remains covered separately by the Docker matrix. The container can write dependency setup and bind-mounted reports without changing checkout ownership. Its ephemeral Git configuration trusts only the explicit bind-mounted checkout, avoiding ownership warnings without trusting arbitrary repositories. Only GOTOOLCHAIN is forwarded from the job environment; registry/module downloads still require network access. The container runs `make dep`, then `make verify-mount arch=arm64` for required namespace discovery and the mount package's required namespace-profile tests. Reports are written to the bind-mounted `test/reports/` directory and retained even after failure. This privileged job runs on its own VM, and the test fixture still confines mutations to separate user/mount namespaces. Branch synchronization, release, and the final fan-in job require both verification matrices.

CircleCI documents Arm machine Medium and Large as available on its [Free plan](https://circleci.com/pricing/); they consume the plan's credits. The mount matrix selects Medium to limit resource use. The [machine executor](https://circleci.com/docs/guides/execute/using-linuxvm/) supports privileged Docker containers, unlike the primary Docker executor. Jobs 195/192 establish access, actual Linux 7.0.0-1004-aws arm64, and successful isolated mount operations at both Go versions; remaining credits are organization-specific. The existing environment checks reject a kernel older than Linux 7.0; the VM image name and the Go container image are not kernel-version proof.

Job startup prints the configured executor/image/resource class and records actual kernel/architecture/privilege observations in `environment.json` and job output. Tests require arm64 execution and the supported kernel floor. CircleCI manages the Docker executor's host kernel and does not offer per-job or per-organization kernel selection; changing the Docker image does not select another kernel. The Docker matrix follows that available arm64 runner at both Go versions, currently Linux 7.0. The separate machine matrix must establish its own kernel and mount-operation evidence. Continue observing every run and update the documented verification target when CircleCI changes the runner environment. A runner upgrade does not implicitly change the library's minimum Linux version. See [CircleCI's Docker kernel policy](https://discuss.circleci.com/t/circleci-response-to-cve-2026-43499-ghostlock-linux-kernel-vulnerability/54758), the [configuration reference](https://circleci.com/docs/reference/configuration-reference/), and [Arm execution environments](https://circleci.com/docs/guides/execute/using-arm/).
