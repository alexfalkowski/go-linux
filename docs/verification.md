# Verification

Run commands from the repository root after the submodule bootstrap in [README.md](../README.md). The Go floor is in `go.mod`; CircleCI is the CI owner. [IMPLEMENTATION.md](../IMPLEMENTATION.md) tracks unfinished work and open verification gaps. Commands inherit the trusted operator environment, but diagnostics print only selected kernel/resource observations and validated verification settings.

## Contributor commands

```sh
make dep
make test-environment
make vet
make lint
make scripts-lint
make specs
make coverage
make sec
```

`make dep` uses the shared download/tidy/vendor workflow. Toolchain selection and resolution of the pinned `golang.org/x/sys` dependency may require network access to Go's module proxy/checksum services. Environment discovery requires `uname` and `true` on PATH. `make scripts-lint` requires ShellCheck. `make sec` uses govulncheck and Trivy and may download vulnerability databases. The CI image supplies the quality tools listed in the README; local tool absence is a verification gap, not a pass. `make ci-validate` uses the official CircleCI CLI and its validation API when the CLI/access are available.

`make specs` retains the shared gotestsum runner, race detection, and coverage. It also writes all test events, including output and skips, to `test/reports/specs.json`, alongside `specs.xml` and `profile.cov`. A skipped test is not kernel runtime coverage. Each run replaces those files: archive a run before changing profiles/toolchains if its evidence must be retained. CircleCI stores each job's reports separately. Scope tests with `package=internal/testenv make specs` (or a later implemented package path). The `.gocov` filter excludes the `/test/` directory, retaining coverage of the implemented environment checker and command even though their names contain `test`. Native arm64 and amd64 CI jobs compile and execute package tests through this harness; no separate compile-only or no-cgo check is required.

Reusable resource factories, cleanup, descriptor inspection, bounded asynchronous reads, subprocesses, and mount-namespace setup live in [internal/test](../internal/test). Focused ABI fixtures snapshot procfs descriptors around acquisition after initializing Go polling. They inspect the original descriptor without duplication while cleanup retains its owner, and prohibit concurrent closure during raw observations. Ordinary concurrency scenarios continue through typed public operations; production owners expose no shared inspection interface. Package tests retain their behavior assertions and named input tables. Use descriptive test names because gotestsum prints them as the behavior report. Group related method checks in compact assertion tables when separate passing subtests would obscure the scenario. Executable examples keep ordinary caller code instead of depending on test fixtures.

## Profiles and prerequisite results

| Setting | Values and behavior |
| --- | --- |
| `profile` | `rootless` (default): ordinary-user checks; `namespaces`: additionally request namespace creation/mapping and isolated mount integration |
| `required` | `false` (default): a known unavailable selected prerequisite skips its affected test with a precise reason; `true`: the same result fails the test and command |
| `arch` | Empty (default), `amd64`, or `arm64`; a supplied value must match both the executing Go binary and `uname -m` |
| `kernel` | `supported` (default): Linux 7.0 or later; `7.0`: exactly the baseline major/minor; `newer`: newer than 7.0. A mismatch fails even when the profile is optional. |

Make exports these as `GO_LINUX_TEST_PROFILE`, `GO_LINUX_TEST_REQUIRED`, `GO_LINUX_TEST_ARCH`, and `GO_LINUX_TEST_KERNEL` for the Go command/tests. Invalid settings fail before probing. Set the Make variables at the documented entrypoints rather than relying on inherited values for those four variables.

```sh
make test-environment profile=namespaces
make specs profile=namespaces
make specs profile=namespaces required=true
make specs profile=rootless required=true arch=arm64 kernel=7.0
```

Use `make verify-mount-container image=<Go image reference> arch=<amd64|arm64>` for mount verification locally and in CI. Select the image reference declared in `.circleci/config.yml` and the native host architecture. This shared launcher requires a Linux Docker host that permits privileged containers; it may pull the selected image and download modules. It binds the checkout so reports remain under `test/reports/` on the host.

Inside the container, the launcher runs `make dep`, then `make verify-mount` to record namespace prerequisites and run only the mount package's required namespace-profile tests. That target creates `test/reports/`, writes `environment.json`, and runs the existing race/coverage harness only after discovery succeeds. Discovery or report-writing failure stops the command before tests; unavailable prerequisites fail rather than skip. The target always selects `profile=namespaces`, `required=true`, and `package=mount`. The fixture still isolates operations in separate user/mount namespaces.

Clock-changing timerfd coverage is a separate opt-in mode, excluded from ordinary `make specs` even when run as root. Only inside a disposable VM, with guest time synchronization disabled, run:

```sh
make verify-timerfd-container image=alexfalkowski/go:5.23 arch=amd64 clock_change=true
```

Use the current image from `.circleci/config.yml` and the native architecture. This command changes the Docker host VM's CLOCK_REALTIME; Docker and time namespaces do not isolate that clock. The `clock_change=true` argument explicitly acknowledges this effect and is required before Docker starts. On a VM with the Go tools installed directly, `make verify-timerfd clock_change=true` runs the same suite without Docker. Both entrypoints retain JSON/JUnit/race/coverage reports, enable the `clockchange` Go build tag, and select only the timerfd package. No missing clock privilege is converted to a skip. The fixture restores the original wall clock plus monotonic elapsed time at cleanup; abrupt process termination can prevent restoration, which is why a disposable VM is required.

The added scenarios cover forward/backward cancellation of pending typed reads, ordinary rearming after consuming cancellation, rearming an unread canceled timer while preserving both ECANCELED and the applied setting, and byte/typed periodic reads after expiry followed by a backward jump. The last scenario must block until a real expiration rather than return a false record or EOF. Linux 7.0's nonblocking read path returns EAGAIN when the periodic adjustment yields zero ticks; Go polls again. The defensive `(0, nil)` and `io.ErrNoProgress` conversions remain source-reviewed rather than represented as executed coverage. Required [arm64 job 343](https://circleci.com/gh/alexfalkowski/go-linux/343) and [amd64 job 339](https://circleci.com/gh/alexfalkowski/go-linux/339) at `bff403e` each pass all 76 timerfd events without failures/skips on actual Linux 7.0.0-1004-aws and Go 1.27.4, including these clock-change scenarios.

`kernel=newer` remains an optional selector for an available newer-kernel runner or local checks. It is not a required CI lane. The required runtime targets are the native Linux 7.0 arm64 and amd64 CircleCI runners; update the targets and recorded evidence when those runner environments change.

These are requests to verify an environment, not proof that such runners exist. Default rootless tests can pass on UID 1000 without capabilities. The profile selects tests intended for ordinary users; execution on UID 0 does not establish ordinary-user runtime coverage, so retain the actual UID/capability observations with the results. Namespace creation is probed even during rootless discovery, but a known namespace denial does not invalidate rootless coverage. The namespace profile requests an actual `clone` with user/mount/network namespace flags and one-entry UID/GID mappings; the child executes `true` and exits, with a five-second bound and deterministic process reaping. It performs no mount or network mutation. Successful discovery establishes only creation/mapping prerequisites, not that every filesystem, namespace transition, or privileged facility works.

Diagnostics include Go version, kernel, machine and Go architectures, UID, effective/bounding capabilities, no-new-privileges, seccomp mode, namespace identifiers, selected mount types/options, and cgroup v2 controller observations. Read-only mount/controller observations do not establish writable delegation. The namespace probe's observed error remains visible. It classifies `EPERM`, `EACCES`, `ENOSYS`, or `ENOSPC` from that precise creation/mapping attempt as unavailable prerequisites; it does not infer the responsible seccomp rule or policy. Missing executables, timeouts, unexpected child failures, `EINVAL`, and other unexplained errors fail. An expected permission denial is distinct from successful isolation coverage.

Later package tests must perform their own operation-specific prerequisite checks; do not turn any facility `EPERM` into a blanket skip. Add capability or delegated-resource profiles when an implemented operation first needs them, with its real isolated/delegated resource checks. F02 does not create speculative privilege fixtures for the remaining packages. Mount, route mutation, cgroup delegation, and clock-changing success paths remain separate verification obligations.

## CI and outstanding runners

The `build` job has an architecture matrix: arm64 uses Docker resource class `arm.large`, and amd64 uses `large`. Both use the same Go image and job steps. It runs dependency setup, environment discovery, lint, script lint, security checks, vet, and `make specs profile=rootless required=true arch=<selected architecture>`, followed by coverage generation and upload. Dependency, build, and lint caches are stored separately, following the other Go libraries. Build and lint keys include CircleCI's architecture token, including their fallback keys; module downloads are shared. The ordinary-user suite runs once per architecture, with each job's JSON/JUnit results and coverage retained under `test/reports/`.

Both build jobs use the Go toolchain supplied by the same standard Go image, compatible with the floor declared in `go.mod`. Keep that image and the declared floor aligned when updating Go support. CI has no separately pinned Go-version matrix or toolchain overrides; it exercises the selected image toolchain rather than independently running the minimum patch version. Runtime reports record the actual Go version. Earlier two-version results below remain historical evidence.

The Go image reference is declared once as `&go-image` on its own `image:` line in `.circleci/config.yml`. Both Docker executors and the mount jobs' `GO_LINUX_CI_IMAGE` environment setting reuse it. The CI image updater in the shared scripts repository replaces image tags by line; keeping this reference on a dedicated line preserves that workflow. The script receives the selected reference through the `image` Make argument, so updating the CI tag also updates mount execution and diagnostics.

The required `build-mount` job has the same two-architecture matrix, using the `machine` executor and image `ubuntu-2604:current`: arm64 selects `arm.medium`, and amd64 selects `medium`. Its single run step calls `make verify-mount-container` with the shared image and selected architecture, using the same [scripts/mount](../scripts/mount) launcher as local verification. The script runs that image with `docker run --rm --privileged --user root` so this mount-only lane has effective mount capabilities. Ordinary-user behavior remains covered separately by `build`. The container can write dependency setup and bind-mounted reports without changing checkout ownership. Its ephemeral Git configuration trusts only the explicit bind-mounted checkout, avoiding ownership warnings without trusting arbitrary repositories. Registry/module downloads still require network access. The container runs `make dep`, then `make verify-mount` with the selected architecture for required namespace discovery and the mount package's required namespace-profile tests. Reports are written to the bind-mounted `test/reports/` directory and retained even after failure. Each privileged job runs on its own VM, and the test fixture still confines mutations to separate user/mount namespaces. Branch synchronization, release, and the final fan-in job also require the complete clock-change matrix described below.

The required `build-timerfd` job reuses the mount jobs' machine executors and native architecture matrix, with its own disposable VM for each architecture. It disables guest NTP using `sudo timedatectl set-ntp false`, then runs `make verify-timerfd-container` with the shared image and explicit `clock_change=true` acknowledgment. The privileged container changes only this dedicated VM's clock, with no concurrent mount or ordinary-user lane sharing it. Reports are retained separately. Each job must establish actual clock-setting permission and all scenario assertions; image choice and capability bits alone do not establish coverage.
